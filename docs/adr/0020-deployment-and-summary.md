# ADR 0020: Deployment Target and Research Summary

- **Status:** Accepted
- **Date:** 2026-10-05
- **Related:** ADR 0015 (MLflow), ADR 0017 (Docker), ADR 0019 (monitoring)

## Context

By end of M11 the project has a complete pipeline, tests, docs, and a
read-only Streamlit dashboard that is verified statically. What is
missing is a **public, addressable artifact** — a URL a reviewer can
open without cloning anything — plus a **research-style summary**
that states the methodology, expected outcomes, and honest limits.

Two things complicate deployment:

1. **Data is git-ignored.** `data/` holds the warehouse, features,
   and backtest artifacts. Streamlit Cloud clones the repo and gets
   an empty `data/`; the dashboard would render all tabs empty.
2. **The full pipeline cannot be run inside Streamlit Cloud.**
   yfinance + FRED + ALFRED ingest takes ~30 minutes and depends on
   external APIs. Streamlit Cloud is a presentation host, not a
   compute host.

M12 must produce a public URL that shows the dashboard **populated
with something meaningful**, without pretending to have run the
pipeline in the cloud.

## Decision

We adopt ten decisions.

### 1. Target: Streamlit Community Cloud (free tier)

- URL: `https://<user>-data-backtest-pipeline.streamlit.app` (or
  whatever Streamlit Cloud assigns).
- Free, permanent, GitHub-integrated.
- Auto-redeploys on push to `main` (webhook-driven by Cloud).
- No paid tier, no custom domain.

A VPS (Docker + reverse proxy) is documented as an alternative in
`docs/runbook.md` but not used. Streamlit Cloud is the primary and
only supported deployment target.

### 2. Demo mode: dashboard falls back to committed sample data

The dashboard reads from `data/` **if it exists**, else from
`data_demo/` (committed). The selection is made by a single
`_resolve_root()` function in `app/streamlit_app.py`. There is no
env var to toggle; the presence of `data/` wins.

Rationale: a reviewer on Streamlit Cloud gets a populated dashboard;
a developer on their own machine gets their real data. No manual
switch, no configuration drift.

### 3. Sample data: synthetic, small, committed

`data_demo/` contains:

| File | Size | Purpose |
|---|---|---|
| `warehouse_demo.duckdb` | ~200 KB | 4 marts, tiny rows |
| `features_demo.parquet` | ~50 KB | ~200 trading days × 3 tickers |
| `backtest/demo_run/metrics.parquet` | ~5 KB | 8 synthetic folds |
| `backtest/demo_run/table_pooled.parquet` | ~3 KB | Pooled summary |
| `backtest/demo_run/equity_curves.png` | ~30 KB | Pre-rendered plot |
| `backtest/demo_run/calibration.png` | ~20 KB | Pre-rendered plot |
| `monitoring_demo.json` | ~5 KB | Pre-built monitoring report |
| `README.md` | — | Explains what this is |

Total under 500 KB. Fits comfortably in git.

**The data is synthetic and clearly labeled as such.** A banner at the
top of every tab says "DEMO DATA — synthetic, not real market data."
Reviewers see the dashboard populated; nobody mistakes it for a real
backtest.

### 4. Sample data is generated by a script, not by hand

`scripts/make_demo_data.py` produces all files in `data_demo/`
deterministically. Seeded. Re-run at any time to regenerate. This is
the single source of truth for demo content; the committed files are
an artifact.

Rationale: the generator documents the schema and provides a way to
refresh the demo when the schema changes.

### 5. Demo banner: prominent, unmissable

Every tab renders a colored banner at the top when running from
`data_demo/`:

```
⚠️ DEMO DATA — synthetic market, not a real backtest.
   See data_demo/README.md for details.
```

Colored `:orange[]` in Streamlit, with the file link. No hidden
toggle. If the deployment looks "real" and someone reads the numbers
as real, we have failed.

### 6. Research summary format: Markdown, paper-like, in `docs/`

`docs/research_summary.md` follows a research-paper structure:

1. Abstract
2. Problem statement
3. Data (universe, sources, PIT design)
4. Features (families, anti-leakage)
5. Model (logistic regression, calibration)
6. Risk framework (quarter-Kelly, limits)
7. Backtest methodology (walk-forward, deflated Sharpe)
8. Results
9. Limitations
10. Conclusion
11. Reproduction

Markdown only. No PDF. No LaTeX. The repo is the artifact.

### 7. Research summary: results section is honest about the state

The **Results** section has two parts:

- **Expected outcomes** — what we anticipate: AUC ~0.51-0.53,
  Sharpe ~0-0.5 after cost, likely underperformance vs SPY
  buy-and-hold. These are stated *a priori* so they cannot be
  retrofitted to whatever the numbers end up being.
- **Observed outcomes** — a table with placeholder rows and a clear
  note: "to be filled after running `make pipeline` on a local
  machine with network access. The Colab environment this project
  was developed in cannot run the full ingest."

Rationale: writing the expectation first, then the observation, is
the correct order. If the observed AUC lands at 0.60, that is a
signal of a bug, not a triumph; the prior expectation is what makes
that visible.

### 8. No CI/CD deploy check

CI (ADR 0018) does **not** verify the Streamlit Cloud deploy. There
is no automated test that the URL is alive. Rationale: the deploy is
a UI-driven action; a deploy check would require secrets and would
fail loudly on transient Streamlit Cloud issues, blocking unrelated
PRs.

Manual verification: after a deploy, the maintainer opens the URL,
clicks each tab, and confirms the demo banner appears. Documented in
the runbook.

### 9. VPS alternative: documented, not built

`docs/runbook.md` describes a Docker-based deploy (Dockerfile from
ADR 0017 + a Caddy reverse proxy in front of `streamlit run`). Not
built in M12. Rationale: Streamlit Cloud is sufficient for a
portfolio project; a VPS adds cost, ops, and TLS management for no
additional signal.

### 10. Deployment is documented in two places

- **README**: a single "Live demo" line at the top with the URL.
- **`docs/runbook.md`**: the full procedure, including how to
  regenerate `data_demo/`, how to trigger a redeploy, and how to
  debug a failed deploy.

Rationale: the URL belongs in the README for reviewers; the mechanics
belong in the runbook for the maintainer.

## Consequences

### Positive

- A public URL that shows the dashboard populated with plausible data.
- No pretending: demo mode is prominently labeled.
- The research summary is written in the correct order (expectation
  first, observation second), which forces honesty.
- The sample data generator doubles as documentation of the schema.
- Zero ongoing infrastructure.

### Negative

- The dashboard on Streamlit Cloud is **not** a real backtest. A
  reviewer who wants real numbers must run the pipeline locally.
  This is clearly stated but is still a limitation.
- Sample data drifts if the real schema changes. Mitigated by
  re-running `make_demo_data.py` and committing; not caught by CI.
- Streamlit Cloud free tier has cold starts (~30 s) after inactivity.
  Acceptable; documented in the runbook.

### Neutral

- No custom domain, no analytics, no auth. Public read-only
  dashboard.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Run the pipeline in Streamlit Cloud | External APIs, 30 min runtime, no persistent storage |
| Ship real data in the repo | Licensing, size, updates |
| No deployment at all | Portfolio project needs an addressable artifact |
| VPS with Docker | Ops cost for no additional signal |
| Heroku / Fly.io | Paid or sunset; Streamlit Cloud is purpose-built |
| Hugging Face Spaces | Viable, but Streamlit Cloud is the canonical host for Streamlit apps |
| Write the research summary with synthetic numbers | Dishonest |
| Wait for real run before writing any summary | Blocks M12 indefinitely; the methodology is the value |
| Hide the demo banner to look "real" | Defeats the point of the project |
